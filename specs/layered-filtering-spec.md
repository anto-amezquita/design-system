# Layered filtering for DataTable — specification

Companion to the dense-data research at `amezquita.dk/dashboard-ux-patterns`. `DataTable` currently sorts, paginates, and selects, but has no filtering at all — the single largest gap between the component and the research's "layered filtering, not one giant panel" pattern. This spec adds column-level filtering natively to `DataTable`, and a slot for app-level global filters, without turning the component into something that owns app-specific fields (date range, category, market) it has no business knowing about.

**Why this matters:** the research is explicit that a single filter panel forces a context switch, while filters living close to the data they filter — in the column headers — let someone answer "show only the ones below a threshold" without leaving the table. That's the gap here.

---

## Current state

`DataTable<T>` (`components/patterns/DataTable/DataTable.tsx`) owns sort, pagination, and row-selection state internally, all `useState`-driven, with careful ref-based patterns to avoid stale closures across batched updates (see `onSelectionChangeRef`, `sortedRef`, `pendingSelectionCallbackRef`). `Column<T>` currently has `key`, `label`, `sortable`, `width`, `render` — no filter-related fields. There is no filter UI anywhere in `Table` or `DataTable`, and no global filter bar slot. `Input` (with a built-in `search` variant) and `Select` (Radix-based, controlled) already exist as primitives and are the natural building blocks for filter controls — this spec should reuse them, not invent new filter-input components.

---

## What "layered filtering" means here

Two layers, per the research, with two different owners:

1. **Column-level filters** — narrow, scoped to one column's data (e.g. "status = active", "name contains…"). These are generic and data-driven, so `DataTable` can and should implement them natively.
2. **Global filters** — broad, app-specific (date range, category, market). These aren't things `DataTable` can know about generically. `DataTable` should not try to build UI for these; it should expose a slot so a consuming app can place its own controls above the table, while `DataTable` still applies whatever filtered state results.

## Fix direction

1. **`Column<T>` gains filter fields.** Add `filterable?: boolean`, `filterType?: 'text' | 'select'`, and `filterOptions?: { value: string; label: string }[]` (required when `filterType: 'select'`). Mirrors how `sortable` already works on the same type — don't invent a parallel config shape.
2. **A filter row, rendered by `DataTable` when at least one column is filterable.** Second header row beneath the label/sort row, one cell per filterable column, using `Input` (search variant) for `text` and `Select` for `select`. Non-filterable columns get an empty cell so column alignment holds.
3. **Filter state lives in `DataTable`, dual-mode like `Input`/`Select` already are.** Internal `useState` by default (uncontrolled), but accept an optional `filters`/`onFiltersChange` pair so a consuming app can lift the state out — this is what makes saved views possible later without `DataTable` needing to know what a "saved view" is. Reuse the existing `useUncontrolledValue` pattern already used by `Input` rather than a new mechanism.
4. **A `toolbar` (naming TBD — see open questions) slot prop** rendered above the table, for the app's own global filter controls (date range, category, market). `DataTable` renders whatever's passed; it doesn't know or care what's inside it. This keeps `DataTable` from ever needing app-specific fields.
5. **Filtering interacts with existing state the same careful way sort/selection already do:** filtering resets `currentPage` to 1 (same as `pageSize` changes already do); the row count announcement (`data-table__count`, already `aria-live="polite"`) must reflect the filtered count, not the total; sorting and pagination operate on the filtered set, not the raw `data` prop.

## Open questions to resolve before coding

1. **Selection behavior when a selected row is filtered out.** Existing behavior keeps selection across pages (selection is index-based into `sorted`, not `pageData`). Filtering changes what indices mean. Decide: does filtering out a selected row silently drop it from the selection, or persist it invisibly until the filter is cleared? Audit the existing selection-index logic (`selectedIndices` is a `Set<number>` over `sorted`, not `data`) before deciding — this may need selection to move to a row-identity keyed structure (`getRowKey`, which already exists for a different reason) rather than positional indices, once both sort *and* filter can each reorder/resize the array between renders.
2. **Toolbar slot naming and shape.** Recommend a single `renderToolbar?: (filteredCount: number, totalCount: number) => React.ReactNode` prop rather than a bare `React.ReactNode`, so the app's global filter bar can show "12 of 340" without re-deriving it — but confirm this doesn't overlap awkwardly with the existing `data-table__count` footer text once both exist. Decide during implementation, record the reasoning here.
3. **Where filter row CSS lives.** `DataTable.css` currently owns table-specific layout; `Table.css` owns generic table primitives. The filter row is DataTable-specific (Table itself has no concept of filtering) — confirm it belongs in `DataTable.css`, not `Table.css`, before adding styles.
4. **Debouncing text filters.** Filtering on every keystroke against a large in-memory array is fine at the client-side scale this component already targets (~1,000 rows, per the dense-data research), but confirm whether `Input`'s existing `onChange` firing per-keystroke is acceptable as-is or needs a debounce — check whether any other part of this repo already has a debounce utility before writing a new one.

## Acceptance

- A `DataTable` with at least one `filterable` column renders a filter row; typing in a text filter or choosing a select filter narrows visible rows without a page reload, resets to page 1, and updates the `aria-live` row count.
- Filtering, sorting, and pagination compose correctly in any order (filter then sort, sort then filter, filter then paginate) — verify with a dataset that requires more than one page after filtering.
- `renderToolbar`/toolbar slot (name per open question 2) renders whatever the consumer passes, unmodified, above the table.
- Selection behavior across a filter change matches whatever open question 1 decides, and is covered by a test that filters, selects, clears the filter, and confirms the selection state is what the decision says it should be.
- Every filter input has a real accessible name (label or `aria-label`) — same WCAG 4.1.2 bar the rest of this repo already holds itself to (see `Input`'s own dev-mode warning for a missing label, and `TableHeader`'s sort-button `aria-label` fallback).
- `npm run validate` passes.
- Existing `mcp-server-spec.md` Phase 6 cold-test tasks (`SettingsPanel.tsx`, `ComparisonTable.tsx`) still pass unmodified — this feature must not change `Table`'s or `DataTable`'s existing documented behavior for consumers who don't use filtering.

## Process — match the existing specs' discipline

1. **Audit.** Read `DataTable.tsx`'s current state-management patterns closely (especially the selection-index logic flagged in open question 1) before writing any filter code — the ref-based patterns already in this file exist for specific stale-closure reasons; new filter state needs to follow the same discipline, not a shortcut.
2. **Resolve the four open questions above**, recording the decision and reasoning in this file's Session log, the same way `compound-component-docs-spec.md` did.
3. **Implement**, reusing `Input`/`Select` for filter controls and `useUncontrolledValue` for the dual-mode state — no new filter-input components unless the audit shows a real gap `Input`/`Select` can't cover.
4. **Review gate** — a real read-through, not a self-assessment: confirm filter+sort+pagination compose correctly in every order, confirm the selection decision from open question 1 actually holds under a filter-then-clear cycle, confirm no regression to `DataTable`'s existing sort/selection/pagination behavior for tables with no filterable columns (must degrade to exactly today's behavior).
5. **Cold test** — run the new task above, two consecutive clean runs.
6. **Document** — update this file's Session log, and note in `mcp-server-spec.md`'s backlog (or wherever the roadmap tracks robustness work) that layered filtering is done, the same way `compound-component-docs-spec.md`'s closure was logged there.

## Out of scope, deliberately

- **Saved views** (naming and persisting a filter+sort+page state as a named view). The dual-mode `filters`/`onFiltersChange` prop from Fix direction #3 is what makes saved views buildable by a consuming app — actually building "save this view" UI is an app-level product feature, not something the design system component should own.
- **Global filter bar UI itself** (date range pickers, category selects). Only the slot for it. These fields are app-specific; the design system has no generic "category" or "market" concept to build a component around.
- **Server-side filtering.** This spec targets the same client-side scale the rest of `DataTable` already targets. Server-side filtering is a `DataTable`-scale/architecture question that belongs with the scale/progressive-disclosure work, not here.
- **Sticky headers/first column, delta cells, density toggle** — the other three recommendation areas from the dense-data review. Separate specs if pursued.

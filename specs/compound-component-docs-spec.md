# Compound component & usage-example accuracy — specification

Companion to `docs/mcp-server-spec.md`'s Phase 6 cold-test findings. Fixes the two real, out-of-scope gaps that phase logged: `Card`'s sub-components have no tool-reachable prop data, and `Table`'s compiled usage example is a Storybook-only placeholder rather than real markup. Both are upstream doc-generator gaps, not MCP-server bugs — this spec is where they get fixed.

**Why this matters:** the whole point of the AI-readiness work is an agent that doesn't guess. Both gaps currently force an agent to guess anyway — either because a real sub-component has no documented shape, or because the one "usage example" on file isn't real usage.

---

## Problem 1 — compound sub-components aren't independently documented

`Card` is used with `CardHeader`, `CardTitle`, `CardDescription`, `CardFooter` — shown in Card's own usage example — but only `Card` itself is registered in `tokens/component-registry.json`. Asking `get_component` for `CardTitle` returns the same "doesn't exist" error as a genuinely made-up name, even though it does exist and has real props (e.g. an `as` prop mentioned in Card's own Accessibility notes).

### Root cause
`scripts/build-component-registry.mjs` (confirm exact name before editing) walks top-level exported components only. It never looks for sub-components attached as static properties (`Card.Header = CardHeader`) or exported alongside the parent.

### Fix direction
Two parts, in order:

1. **Export convention.** Compound sub-components must be authored so a docgen tool can actually see them: exported as their own named `const`, then attached to the parent afterward — `const CardHeader = (...) => {...}; Card.Header = CardHeader;` (or the existing pattern in this repo, whichever direction — audit `Card.tsx` first to see what convention is already in use before changing it). `react-docgen-typescript` has native support for this exact shape but is fussy about it; nested/class-style attachment doesn't work reliably.
2. **Registry generator extension.** Extend `build-component-registry.mjs` to also walk each component's static sub-components and register them as their own entries — either as first-class registry entries (so `get_component("CardTitle")` resolves directly) or as a nested `subComponents` field on the parent entry (so `get_component("Card")` returns the whole family in one call). **Decide which shape before implementing** — see Open question below.

### Open question to resolve before coding
Nested field vs. independent registry entries changes the MCP tool contract (`get_component`'s output shape) and the cold-test agent's calling pattern. Recommend: independent registry entries, prefixed or namespaced clearly (e.g. `slug: "card-header"`, with a `parent: "card"` field), since that matches how `get_component` is already called today (one name/slug at a time) and needs no MCP tool code changes — only the registry generator changes. Confirm this against how many other components in the repo already use the compound pattern (audit first, don't assume Card is the only one).

### Acceptance
- `get_component("CardHeader")`, `("CardTitle")`, `("CardDescription")`, `("CardFooter")` all resolve with real props — re-run the exact cold-test task from `mcp-server-spec.md` Phase 6 Run 1 (`SettingsPanel.tsx` using `Card`/`Switch`/`EmptyState`) and confirm the agent no longer has to infer Card's sub-component props.
- Audit whether any other compound components in the repo (check the full component list, not just Card) have the same gap; fix all of them in the same pass, not just Card.
- `npm run validate` passes.

## Problem 2 — Table's usage example is a Storybook placeholder, not real markup

`get_component({slug:"Table"})`'s compiled usage example is `<SampleTable />` — a local helper defined in `Table.stories.tsx`, not real `<thead>/<tbody>/<tr>` anatomy. `build-component-docs.mjs` takes the Default story's `render` JSX literally; it doesn't know `SampleTable` is a stand-in.

### Root cause
Same class of problem `expandObjectAliases()` already solved once for prop *types* — inlining a referenced local alias's real shape instead of leaving an opaque name — just never applied to usage examples.

### Fix direction — pick one, don't do both
**Option A (authoring rule, no new code):** Storybook convention — the Default story's `render` must always be the real, inline markup an agent should copy. Any convenience helper (`SampleTable`, etc.) goes in a separately named, clearly-secondary story (e.g. `WithHelper` or `Playground`), never in `Default`. Audit every existing story file for violations of this rule, not just Table's.

**Option B (generator change):** Teach `build-component-docs.mjs` to resolve a referenced local component in the Default story's render output — same inlining `expandObjectAliases()` already does for types, applied to JSX now.

Recommend **Option A** first: it's a convention fix, zero new generator logic, and directly matches the "compiled, not written" discipline the rest of this roadmap holds itself to — a real story is better ground truth than a generator inferring one. Fall back to Option B only if auditing existing stories shows Option A can't be applied cleanly everywhere (e.g. a component that genuinely can't be shown without a data-generating helper).

### Acceptance
- `get_component({slug:"Table"})`'s usage example is real `<thead>/<tbody>/<tr>` markup (or whatever Table's real anatomy is), not a helper reference.
- Audit all Default stories across the repo for the same placeholder-helper pattern; fix any others found in the same pass.
- Re-run the cold-test task from `mcp-server-spec.md` Phase 6 Run 2 (`ComparisonTable.tsx` using `Table`/`Tag`) and confirm the agent gets real anatomy from the tool directly rather than inferring it from prop types and token names.
- `npm run validate` passes.

## Process — match the MCP server spec's discipline

1. **Audit first.** Before writing any fix, audit the actual current state: which components use the compound pattern, what export convention they currently use, which Default stories reference a helper instead of inlining real markup. Don't assume Card and Table are the only affected components.
2. **Decide the open question** (nested field vs. independent registry entries) before implementing, and record the decision and reasoning in this file's Session log.
3. **Implement.**
4. **Review gate**, same bar as `mcp-server-spec.md` Phase 5 — a real read-through against the generators, not a self-assessment, checking specifically for: registry drift (sub-components registered under the wrong parent), a crash on any component that doesn't have sub-components (must degrate cleanly, not error), and any regression to the seven MCP tools' existing behavior (they must still resolve every currently-passing case after this change).
5. **Cold test**, reusing the exact two tasks from `mcp-server-spec.md` Phase 6 (SettingsPanel with Card, ComparisonTable with Table) — these are the tasks that found both gaps, so they're the right regression test for the fix. Two consecutive clean runs, same bar as before.
6. **Document.** Update `mcp-server-spec.md`'s own backlog references to point at this file as resolved, once both problems are closed.

## Out of scope, deliberately

- Rebuilding `build-component-docs.mjs` wholesale — this is a targeted fix to two known gaps, not a rewrite.
- New MCP tools. If Problem 1's registry extension lands as independent registry entries, the existing `get_component`/`list_components` tools should need no code changes at all.
- Any component redesign. This is a documentation/generator/authoring-convention fix, not a component API change (unless the audit in Problem 1 finds an actual export-pattern bug blocking docgen, in which case fix only the export shape, nothing else).

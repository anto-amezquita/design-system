## Item 1 — brand scope

**As decided:** portfolio's files keep `:root, [data-mode="…"]` and add `[data-brand="portfolio"]` and `[data-brand="portfolio"] [data-mode="…"]`.

**Found while building:** as long as `:root` stays in the same file, loading `portfolio-light.css` reskins the whole document, so the added selectors never change what renders: every element already inherits portfolio from `<html>`. The site still couldn't put base next to portfolio on one page.

**Changed, with the user's agreement (2026-10-01):** a separate generated file, `styles/brands/portfolio-scoped.css`, holds the same overrides under `[data-brand="portfolio"]` only. A page loads base as usual plus this file. The existing four files are byte-for-byte unchanged. The selectors, the dark-then-light block order, the union of tokens in both blocks and the `initial` resets for dark-only tokens are explained in 0001's 2026-10-01 amendment. `lib/brand-scope.test.ts` checks in Chromium that a scoped panel computes every custom property exactly as a whole page does with the unscoped files.

## Item 5 — MCP tool list

`scripts/mcp-server.mjs` registers its tools through one small wrapper that records each tool's `name`, `title` and `description`, and exports that list. The transport only connects when the file runs as the entry point, so the build can import it without starting a stdio server.

`build-llms-txt.mjs` imports the list:

- `llms.txt` gets an "MCP server" section: each tool's name and the first sentence of its description.
- `llms-full.txt` gets the full descriptions.

The server isn't in the package's `files`, so the section says it runs from a clone of the repo (`node scripts/mcp-server.mjs`). `AGENTS.md` is hand-written, not generated, so it keeps its pointer and doesn't get the list.

A test asserts that `llms.txt` lists exactly the tools the server registers.

## Item 6 — token descriptions

**What exists:** 48 tokens have a `$description` (37 in `base/light.json`, 4 in `portfolio/tokens.json`, 4 in `global.json`, 3 component tokens). `build-token-reference.mjs` copies none of them: every entry in `token-reference.json` lacks the field.

**What changes:**

- `build-token-reference.mjs` adds `description` to each entry that has one. For a token defined in both base and portfolio, base's description wins (it describes the role, which is what every consumer gets); portfolio's is the fallback. Primitives carry theirs too.
- Every semantic token in `base/light.json` and every component token gets a one-line `$description`: what it's for, in plain words. Existing descriptions stay as written.
- Primitives don't get new descriptions. Their names are their values (`gray-500`, `space-4`), and they're deliberately not offered for use.
- Any token whose purpose isn't clear from its name, value and usage is listed in the PR instead of guessed.

## Item 7 — fonts

The package ships no font files (decided). `tokens/fonts.json` is generated by `npm run tokens` and shipped in the package:

```json
{
  "brands": {
    "base": {
      "families": [{ "family": "JetBrains Mono", "tokens": ["font-family-mono"], "weights": [400, 500, 600, 700, 800] }],
      "href": "https://fonts.googleapis.com/css2?family=JetBrains+Mono:wght@400;500;600;700;800&display=swap",
      "preconnect": ["https://fonts.googleapis.com", "https://fonts.gstatic.com"]
    },
    "portfolio": { "...": "Schibsted Grotesk and JetBrains Mono" }
  }
}
```

- **Families** come from each brand's resolved `font-family-*` tokens: the first family in the stack, when it's a named web font rather than a system stack. Base's text stacks are system fonts, so base only needs JetBrains Mono. Portfolio is a skin on base, so it needs Schibsted Grotesk and base's JetBrains Mono.
- **Weights** are every value the brand's font-weight tokens (semantic and component) resolve to. Both families are variable fonts on Google Fonts, so listing more weights doesn't add downloads.
- A family the generator doesn't know how to load (not in its Google Fonts list) fails the build, so a new brand font can't ship undocumented.
- `llms.txt` and `llms-full.txt` get a "Fonts" section with each brand's link. The README names the families and points at `tokens/fonts.json` rather than copying links that would drift.

ADR `0020` records it, with self-hosting and `@font-face` in the package as rejected alternatives.

## Backlog item 3 — why `changelog.json` is a release behind

`build-changelog.mjs` groups commits by git tag. The tag for a release (`v1.1.2`) is created by `changeset publish` in `release.yml`, after the tarball's contents are already fixed by the Version Packages merge commit. So the package for version X always ends at X−1, with X's own commits under `unreleased`. The installed `1.1.2` ends at `v1.1.1`; the portfolio's `1.1.0` ends at `v1.0.0`. On `main`, X shows up only after the next push, since the tag push doesn't trigger `update-changelog`.

Not a small, obvious fix: it needs the builder to label untagged commits with `package.json`'s version when that version has no tag yet, *and* `release.yml` to rebuild the changelog before publishing, which touches 0019's "main owns it" split. Left in the backlog with this cause.

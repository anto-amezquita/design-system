# MCP server — specification

Local-first, read-only. Exposes what the repo already generates, live, instead of as a static snapshot. Companion to [`ai-readiness-plan.md`](./ai-readiness-plan.md) — that plan intentionally skipped this (Phase 0/5: "deliberately out of scope"); this file is the spec for picking it back up.

**Why now:** solo maintainer today, so a static snapshot (`llms.txt`, the skill file) never goes stale between reads. The trigger for building this anyway is a possible near-term shift to a team — a second consumer whose agent needs current state, not a snapshot from the last `npm run tokens`. Building it locally, unhosted, costs nothing and means the shape already exists if that shift happens.

**Scope discipline, same as Phase 4:** a fraction of the surface of a full read/write API, most of the value. Read-only. No new data, no new generators — every tool wraps a file this repo already produces.

## What it wraps, not what it builds

Every tool below reads a file this repo's existing generators already produce. No tool computes anything new.

| Data | Already generated by | Read by tool |
|---|---|---|
| Component list, tier, purpose, props, tokens, stories | `scripts/build-component-registry.mjs` → `tokens/component-registry.json` | `list_components`, `get_component` |
| Per-component compiled doc (props, tokens, usage) | `scripts/build-component-docs.mjs` → `docs/components/<slug>.md` | `get_component` |
| Resolved token values, all 4 axes | `scripts/build-token-reference.mjs` → `tokens/token-reference.json` (also published as `tokens.json`) | `get_token`, `search_tokens` |
| Fabrication rules (no raw hex, no fallback, real prefixes) | `scripts/lint-tokens.mjs` | `validate_token` |
| shadcn-spec registry item per component | `scripts/build-registry-manifests.mjs` → `registry/<slug>.json` | `get_registry_item` |
| Agent skill content | `scripts/build-skill.mjs` → `skills/amezquita-design-system/SKILL.md` | `get_skill` |

If a tool's answer isn't in one of these files, the tool doesn't exist yet — same "compiled, not written" discipline as the rest of the roadmap. Don't let an MCP tool become a second place logic can drift from the generators.

## Tools

| Tool | Input | Output | Source |
|---|---|---|---|
| `list_components` | optional `tier` (`primitives`/`composition`/`patterns`) | name, slug, tier, purpose, tokenCount for each public component | `component-registry.json` |
| `get_component` | `name` or `slug` | the compiled `.md` twin content — props (unions expanded), tokens, usage example | `docs/components/<slug>.md` |
| `search_tokens` | `query`, optional `category` | matching token entries: name, cssVar, type, resolved value per axis | `token-reference.json` |
| `get_token` | exact token `name` | full entry: raw value, resolved per axis, `usedBy` | `token-reference.json` |
| `validate_token` | a `var(--x)` string or bare token name | `{valid: bool, reason}` — same checks as `no-fabricated-token` / `no-token-fallback` | reuses `lint-tokens.mjs` logic |
| `get_registry_item` | component `slug` | the shadcn-spec `registry-item.json` content (for an agent deciding whether to `npx shadcn add` vs. hand-write) | `registry/<slug>.json` |
| `get_skill` | — | current `SKILL.md` content | `skills/amezquita-design-system/SKILL.md` |

Seven tools. Resist adding an eighth without a concrete failure it fixes — the same rule Phase 4's cold-testing enforced on the skill file.

## Architecture

- **Process:** a single Node script (`scripts/mcp-server.mjs`), using `@modelcontextprotocol/sdk` (new devDependency — not currently in `package.json`). Runs over stdio, launched by the MCP client (Claude Code) per-session — no daemon, no port, no process to remember to start.
- **State:** none held in memory beyond what's read per-call. Every tool call does a fresh `readFileSync` of its source JSON/MD — correctness over throughput, since these files are small (`token-reference.json` is ~227 KB, the rest smaller) and call volume is low.
- **No new generators.** `validate_token` is the one tool with logic beyond a file read; it must import and reuse the actual predicate functions from `lint-tokens.mjs` (refactor those into an exported function if they're not already), not reimplement the fabrication rules a second time.
- **Auth:** none. Read-only, local-only, no write path — nothing to gate yet. Revisit if this ever moves to hosted (see "Local → hosted" below).
- **Registration:** add an entry to `.mcp.json` (or the equivalent Claude Code project config) pointing at `node scripts/mcp-server.mjs`, committed to the repo so any clone gets it automatically — same "checked into the repo, not hand-configured per machine" instinct as `AGENTS.md`.

## Testing — cold, like Phase 4

Phase 4's acceptance test is the template: a fresh subagent, no memory of this repo, given only the MCP tools (not the skill file, not `AGENTS.md`) and a real task — e.g. "add a Tag to this page, check what variants exist, and confirm the tokens you used are real before you finish." Watch for:

- Does it call `list_components`/`get_component` before guessing a prop shape, the way the skill-file test caught the `Select.groups` gap?
- Does it call `validate_token` before finishing, or only when told to?
- Does any tool response get truncated or malformed for a component with edge cases already on record (EmptyState's missing token file, Toast's missing props type) — those are known "omit the section, don't crash" cases from Task 1.2; the MCP wrapper must preserve that, not regress to a crash or an empty-looking section.

Re-run once after fixing whatever the first pass finds, same as Phase 4 did twice.

### Phase 5 reviewer notes

Consolidated review across all seven tools together — distinct from the four per-phase reviews already run against each phase's own diff. Method: eight parallel finder angles (line-by-line, removed-behavior, cross-file trace, reuse, simplification, efficiency, altitude, conventions) against the full accumulated file, plus direct fault-injection testing (corrupting and restoring `tokens/component-registry.json`, `tokens/token-reference.json`, and `skills/index.json` one at a time against a live MCP client) that the automated reviewers' diff-based approach couldn't reach on its own — that's what found the startup-crash issue below.

- **list_components** — Checked: fresh read per call (confirmed, no caching), `TIERS` enum staleness if a tier is added mid-session (accepted tradeoff, documented inline — zod needs a static schema before the transport connects, there's no per-call hook to defer to). Nothing broke specific to this tool. Benefits from the cross-cutting startup-crash fix below.
- **get_component** — Checked against `docs/components/<slug>.md`'s real generator and both named edge cases (EmptyState's missing token file, Toast's missing props type) — both resolve without crashing, re-verified live. Fixed: its "No public component matches" error text deduplicated into a shared `noSuchComponentError()`, now identical to `get_registry_item`'s (previously two independently hand-typed copies of the same string).
- **search_tokens** — Checked against `token-reference.json`'s real shape. **Broke:** a whitespace-only query (`"   "`) passed `z.string().min(1)` (satisfies length ≥ 1 on the raw string) but became `""` after the handler's own `.trim()`, and `"".includes()` is always `true` — so a whitespace query silently returned all 620 tokens instead of erroring. **Fixed:** the zod schema now does `.trim().min(1, ...)`, rejecting whitespace-only input before the handler runs at all; confirmed both empty-string and whitespace-only queries now correctly error.
- **get_token** — Checked exact-match behavior for both `"space-4"` and `"--space-4"` input forms against real data — both still work. **Found, not a live bug:** the match predicate compared a normalized `varName` against `cssVar` but an *unnormalized* raw `name` against `t.name` in the same expression — never produced a wrong result for any real token name (dead code, confirmed by trace), but confusing to read. **Fixed:** both sides now compare against the same normalized value.
- **validate_token** — Checked that it genuinely calls `lint-tokens.mjs`'s real predicates (confirmed, not reimplemented) across the original six input shapes from Phase 3 plus new adversarial ones. **Broke, most severe finding of this pass:** its own tool description claimed "a tool pass here means the lint pass will also be clean" — false. It never checks `no-primitive-tokens`; confirmed live that `validate_token({token: "var(--color-warm-500)"})` returns `valid: true` even though that exact reference fails `npm run tokens:lint` for real (primitives are banned in component CSS, semantic tokens aren't). A second, lower-severity bug: a fallback-form violation's diagnostic was silently discarded when the same input also had unparseable trailing content (`"var(--space-4, 16px) foo"`) — the collected reason got replaced by a generic "not recognized" message with no mention of the fallback problem that was already found. **Fixed:** description rewritten to state the tool's actual, narrower scope and name what it explicitly can't check (`no-primitive-tokens`, and a CSS file's own locally-declared custom properties, which `no-fabricated-token` itself only allows with file context this tool doesn't have); the fallback reason now survives into the unparseable-input path instead of being discarded. Also deduped a redundant double `RADIX_VAR_RE.test()` call per invocation.
- **get_registry_item** — Checked against `registry/<slug>.json`'s real generator and the same edge cases (EmptyState's empty `cssVars`, Toast's item despite no props type) — both resolve cleanly, re-verified live (Toast's registry item wasn't actually tested until this pass — it was, and works). Fixed: shares `get_component`'s deduplicated error text (see above) instead of a second hand-typed copy.
- **get_skill** — Checked against `skills/index.json`'s real (single-entry) shape. **Found:** `index.skills[0]` had no bounds check — every other lookup in this file produces this file's own actionable error style on a missing precondition; this one path would have thrown a raw `TypeError` if the array were ever empty. Currently unreachable (confirmed exactly one entry exists today) but not defended against. **Fixed:** explicit bounds check added, matching the file's established pattern everywhere else.

**Cross-cutting fixes, not specific to one tool:**
- `CATEGORIES` was independently re-derived from whichever categories happen to appear in the live `token-reference.json`, when a canonical source already exists: `lib/token-categories.mjs` exports `TOKEN_CATEGORIES`, and its own header comment explicitly warns against exactly this kind of drift (`build-token-reference.mjs`'s `getCategory()` and the docs site's `TokenTable.tsx` filter pills both already import it). Fixed by importing `TOKEN_CATEGORIES` directly instead of re-deriving a third copy — this also removed one of the two startup-time `tokens/*.json` reads entirely, since `CATEGORIES` no longer needs `token-reference.json` at all before the transport connects.
- **Found by direct fault injection, not by any of the eight automated finder angles:** `TIERS`/`CATEGORIES` were computed at module load (required — `registerTool()`'s zod schema must exist before `server.connect()`, there's no per-call hook to defer to), but unlike every one of this file's own per-call reads, a malformed or mid-rewrite `tokens/component-registry.json` at that moment killed the *entire* server with a raw Node stack trace and an opaque "Connection closed" on the client side — not the clean, actionable one-liner every other failure path in this file produces. Confirmed live: backed up the three JSON files this server reads (`component-registry.json`, `token-reference.json`, `skills/index.json`), corrupted each in turn, observed the actual failure mode, restored from backup, and verified the restored file's checksum matched the original before moving to the next. `component-registry.json` corrupted at startup crashed the whole connection (now fixed — see below); `skills/index.json` corrupted degraded gracefully into a normal tool-level error, since it's read inside `get_skill`'s own handler, not at module load — confirmed `list_components` and every other tool were completely unaffected while `get_skill` alone reported the break. This asymmetry (startup-time reads vs. per-call reads) is now fail-fast-but-clean rather than fail-fast-and-ugly: the startup read is wrapped in `try/catch`, printing one clean line to stderr and exiting, instead of an unhandled-exception trace.
- `npm run validate` re-run clean after every fix in this pass, not just once at the end.

## Local → hosted, if the team scenario materializes

Not scoped here — recorded so the next session doesn't have to re-derive it. If a second real consumer (e.g. a BESTSELLER frontend/backend team) starts using this concurrently:

- Swap stdio for an HTTP/SSE transport (the SDK supports both) and host it somewhere persistent — a small always-on process, not a rebuild of the tool logic above.
- Add read-only auth (an API key or similar) once it's reachable over the network instead of only over local stdio.
- Everything in the "Tools" table stays the same — the trigger for hosting is *reachability*, not a change in what the tools do.

## Out of scope, deliberately

- **Write tools.** No `add_component`, no `update_token`. This is a read-only reference surface, matching the rest of the AI-readiness work's scope discipline.
- **A second data layer.** If a fact isn't already in `component-registry.json`, `token-reference.json`, `registry/*.json`, or the compiled `.md` twins, this spec doesn't add a new generator to produce it — that's a separate roadmap item, not part of this one.
- **CLI or editor-rules integration.** Same as `ai-readiness-plan.md`'s Phase-4 framing — not attempted this round.
